    • What is it?

    TestFlows™ Machine is a deterministic execution environment where you run, explore, debug and test your software. It is built on our deterministic hypervisor, which runs your programs, Docker images and Docker Compose environments unchanged.

    Nothing in the machine is left to chance. It controls time, interrupts, random numbers and input from devices, and it records all of them while your program runs. Replay the recording and the program does exactly what it did the first time, instruction for instruction.

    That gives you three things to work with:

    • Record. Every run keeps a log of everything that could have turned out differently.
    • Replay. Play the log back and the run repeats itself. If it failed once, it fails every time.
    • Branch. Stop at any point, branch from it, and try something else. The original run stays as it was.

    If you have ever chased a test that fails one run in fifty, you know why this is handy. Record the failing run once, then replay it as often as you need.

    You work with Machine through a client called machine, or from Python using the SDK. To begin, install the client. It is one command.

    Concepts

    There are only a few of them, and the rest builds on them.

    Disk. What a machine boots. It is your program (or a whole application) packaged with a small Linux system. You build one with machine disks build.

    Session. The vCPUs and RAM you allocate, which one or more runs execute in. It is what you are billed for, from the moment you create it until you delete it, so delete it when you are done.

    Run. A deterministic machine booting a disk inside a session. Every run has a name. Nearly every action is something you do to a run.

    Entry. A run writes its history as a log. Each item in the log is an entry, so for example, entry #42 is always the same point in that run.

    Checkpoint. A saved copy of the whole machine at one point in the log. Every run has checkpoint 1, taken at its first entry, and you can add your own and name them.

    Branch. A run that starts from another run at some point. It shares history with its parent up to that point and has its own after that. You create one with machine fork or machine go. Runs that grow out of one another form a tree.

    Mark. A second name for a branch, given after the fact. The generated name says where a branch started. A mark says what it turned out to be, like crashed.

    Points

    A lot of commands take a point, which is a place in a run’s history. You can name one in several ways.

    Point Means
    ^booted the checkpoint named booted
    #42 entry 42
    1.5s a time on the machine’s clock
    -10ms ten milliseconds of machine time back from where the run is now
    now where the run is now
    parent the point this run branched from
    root the start of the tree
    %crashed the branch with the crashed mark
    console~login where the console first printed a match of login

    The same points work everywhere a point is taken: --at and --from on fork, detach and go, rewind ... to, and replay --to. A bare word is read as a checkpoint’s name first, then as a time, then as an entry, so write ^name or #42 when you mean one of them for sure.

    A branch can only start from a checkpoint. machine go takes any of these points, and if the one you name isn’t a checkpoint, it starts the branch at the nearest checkpoint before it and replays the rest of the way for you. A machine time such as 1.5s or -10ms names the first entry at the last machine time at or before the one you asked for.

    The client

    You work with Machine through a client called machine. Install it with one command:

    That downloads a single binary named machine over HTTPS, checks it against the SHA-256 checksum published next to it, and puts it in ~/.local/bin, with machine-env beside it. If the checksum doesn’t match, nothing is installed. If that folder isn’t on your PATH yet, the installer says so and shows the line to add for your shell. Run the same command again whenever you want to update.

    Supported systems. The client runs on Linux, x86_64 and arm64, and on Macs with Apple Silicon. It needs only the OpenSSH client, which macOS and most Linux systems already have, and the installer never asks for root. If ssh is missing, install it with your package manager, for example sudo apt install openssh-client on Debian and Ubuntu. It doesn’t run on Intel Macs or natively on Windows; on Windows you can use it inside WSL. On an ARM machine, a Mac with Apple Silicon or arm64 Linux, the disks you build must still hold x86_64 programs; see building disks on an ARM machine. If you need another platform, contact us and tell us which one. The download page has the full list, and a way to check the download yourself.

    Behind a proxy that inspects TLS. The client trusts only Let’s Encrypt, which issues the certificate of the Machine API, so a certificate from any other CA is refused, a proxy’s included. The error names TESTFLOWS_MACHINE_API_CA_FILE, an environment variable the client reads: set it to a PEM file of the CAs to trust instead, such as your proxy’s.

    The file replaces the Let’s Encrypt roots rather than adding to them. If the client must also connect without the proxy, add the Let’s Encrypt roots to the same file. The variable applies to the connection to the API alone: sessions are reached over SSH with certificates TestFlows issues, and image pulls use your system’s CAs. A file that is missing or holds no certificate is refused, and the error names the file. The Python SDK reads the same variable.

    On a Mac, use machine-env. macOS ships its own /usr/bin/machine, which prints the processor type, so typing machine may not run the client. Putting the client first on your PATH would hide the system command for every other program. machine-env, which the installer writes on every system, starts a shell in which machine is the client and changes nothing else. Its prompt starts with (machine), your usual shell setup is loaded, and exit leaves. It supports zsh and bash.

    That form runs one command in that environment and starts no shell, which suits scripts and CI. To see which machine you get, run which machine: ~/.local/bin/machine is the client and /usr/bin/machine is the system’s. If machine --version prints a processor type instead of a version, you are running the system command. On Linux, if another command on your system is also named machine, use machine-env the same way.

    To read the installer first, install a specific version or into another folder, check the download by hand, or uninstall, see the download page.

    Run machine with no arguments, or with --help, to see every command. Each command has its own --help too, and that is the place to look when a flag here is not enough.

    machine --version prints the client’s version and its license. Include the version when you report a problem.

    If something does not work, machine ping checks that you can reach the service and your sessions, and how long the round trip takes.

    In machine-env, Tab already completes commands, options and their values, and the names of your runs. Where machine is the client in every shell, as on most Linux systems, add the line for your shell to its startup file to have the same there. On a Mac, use machine-env instead: outside it, machine is the system’s command, and the line would run that one.

    The client answers each Tab itself, from its own commands, so a newer client needs no newer line.

    To try it in one terminal first, run the same line there instead. Tab completes in that shell until it exits, and no other shell changes.

    Signing up

    Create your account on the sign-up page, or from the terminal with machine account signup. Then sign in from the terminal.

    Machine emails you a one-time code and asks for it. You stay signed in until you sign out with machine logout. machine account show tells you who you are signed in as.

    For scripts and CI there is no need to sign in at all. Create an API key and put it in the TESTFLOWS_MACHINE_API_KEY environment variable.

    When you create your first session, Machine sets up your account’s storage first, so that session takes longer to create. To do that step on its own beforehand, run machine account provision.

    Your first run

    If you have not yet signed up and signed in, do that first: see Signing up.

    This example creates a session, builds a disk, runs a program, saves a checkpoint and starts a branch from it. The program is one line of Python, and you need nothing installed but the client: no Docker and no compiler.

    First, create a session. Machine makes it the one your commands use.

    Next, save this as hello.py.

    Build a disk named hello that runs it. --from names the public Python image, --add puts your file in it, and what follows -- is the command the machine runs.

    Only your file is uploaded. The build pulls the image itself and writes it onto the disk, which takes about two minutes for an image of this size. You build a disk once and create as many runs from it as you like.

    A program you compile, an image of your own, or several services together build the same way from other sources. See Disks.

    Create a run from the disk. The machine waits for your commands. With --no-daemon it would boot and run to the end by itself.

    Now the run is waiting. It only moves when you drive it, and machine run is how you drive it. The --until tasks part means “keep going until Linux is up.”

    Read the last five lines the machine printed.

    To see the full console log, use -n :. Ranges use the same colon as a Python slice. Lines are numbered from 1 and both ends count, so -n 1: is the first line through the last.

    A negative number counts from the end, and -1 is the last line. -n -5 and -n -5: are the last five lines, and -n -10:-2 is the tenth line from the end through the second. Both ends of a range count from the same end.

    Save the machine’s state so you can come back to it, and start a branch from that point.

    The checkpoint is in your session. machine sync publishes the run, so the checkpoint outlasts the session and another session can start from it. Stopping the machine publishes it too.

    The branch starts exactly where booted was taken. Notice its full name, hello-run/try-1. A branch is named after the run its tree starts from, a slash, and the name you gave it. Look at the tree.

    Linux is up on the branch and your program has not started yet. Drive the branch until the machine shuts down, which it does when the program exits.

    The program’s own lines start with app-1. Find them in the branch’s console.

    The parent hello-run is still at booted, with the program yet to run. You can fork it again and get the same start every time.

    When you are done, delete the runs and then the session. A run keeps its log and checkpoints until you delete it, and a session costs money until you do.

    That’s the whole loop. You built a disk, saved a point in a run, branched from there and ran a program to its end. Everything else in this page is a variation on it.

    Disks

    A disk is what a machine boots, and machine disks build makes one. You give it exactly one source.

    Source What it takes
    --binary path a static x86_64 executable, wrapped in a scratch image
    --from ref a public image, by name, with the files you add to it
    --image ref a Docker image of your own, as a save tar or a name in your local Docker
    --compose dir a Compose project directory and the images its services name

    Everything a machine runs runs in Docker Compose, inside the machine. A Compose project is one container for each of its services. An image or a binary is a project of one service, and --entrypoint and the arguments after -- are that service’s entrypoint and command. A binary is no exception: --binary wraps the executable in a scratch image, one layer holding that file and nothing else, with no base image, no loader and no libraries, and the machine runs that image as its one service. machine writes this image itself, so --binary needs no Docker on your computer.

    Docker and Compose

    An image of your own needs Docker. A Compose project also needs Docker Compose. Two sources need neither. machine disks build --binary wraps a static executable and nothing else, so a program you compile needs no Docker. The executable has to be self-contained. The image has no loader and no libraries, so a dynamically linked program cannot run. --from names a public image, and the build pulls it for you.

    A program that is not a static executable needs an image that already contains what it runs: an interpreter, a runtime, its libraries.     Where added files go

    --add puts a file or a directory in the image, as one more layer on top of the public one. You can repeat it.

    You write It lands at
    --add hello.py the image’s working directory, as hello.py
    --add conf the working directory, as the directory conf
    --add hello.py:/app/ /app/hello.py
    --add hello.py:/app/main.py /app/main.py
    --add conf:/etc/app/ /etc/app/conf, the directory inside /etc/app
    --add conf:/etc/app /etc/app, the directory’s contents

    The rule is the one cp -r follows: a destination that ends in / is a directory the path goes into, and any other destination is what the path becomes. A Dockerfile ADD of a directory copies its contents; the last row is how you write that here.

    A script that was executable still is. --add works with --binary too, for a program that reads a file beside it.

    --add takes files, directories and links. A device, a FIFO or a socket in the directory is refused. Every added file belongs to root in the image, so the set-user-id and set-group-id bits are not kept: a bit that meant “run as this file’s owner” on your computer would mean “run as root” there.     Carrying images

    A service can start containers of its own, through the machine’s Docker. The images it starts are named by no service this project runs, and a machine reaches no registry, so an image that is not named here is not on the disk.

    Images at boot

    A disk boots with its images already loaded, so the project starts as soon as Docker does.

    A disk built with --load-at-boot keeps the images as docker save tars instead, and Docker loads them each time the disk boots.

    That boot is slower by the whole load, every time, and the disk holds each image twice: the tar, and what it unpacks to. Use it when a service runs docker save or docker push on one of the disk’s own images from inside the machine. Starting containers does not need it.

    Layers compressed with zstd are not read; save the image with gzip or uncompressed layers.

    Disk size

    By default Machine measures what the disk holds and adds a gigabyte, rounded up to a whole GB. Use --size to set the size you want. Not sure how big it will be? --dry-run reports what the disk would hold without building it.

    rootfs is the platform every disk carries. images is the images unpacked, with a layer two images share counted once. used is what a smaller --size is refused against, and the rest of capacity is what the machine can write. With --load-at-boot there is one more row, images (tar).

    To manage your disks:

    machine disks list and machine disks show give two sizes. SIZE is the disk as the machine sees it. DATA is what the disk takes in your account’s storage, after deduplication and compression.

    Disks share what they have in common: every disk carries the same platform, and two disks built from one image share its layers. Storage keeps one copy, and each disk’s DATA counts it, so the column adds up to more than your disks take together. machine storage has that figure, and it is the one your quota counts. A disk that shows — for DATA gets a figure from machine disks verify.

    If you ever doubt the copy of a disk in your account’s storage, check it:

    machine disks verify reads the disk back and computes its ID again. It takes about as long as reading the disk, and a disk that does not read as it was stored is reported as damaged, in which case build it again.

    Deleting a disk is permanent. Machine refuses to delete one that a run still boots, and --force deletes it anyway and takes those runs with it. machine disks transfers shows the transfers in progress, and machine disks cancel stops one.

    Sessions

    Runs live in a session, and you create one with machine sessions create. Pick its size when you create it.

    --cpus sets the number of vCPUs, --mem the memory and --storage the disk space. --class picks the hardware class, and the default comes from your plan. machine sessions classes lists the classes, with the CPU architecture of each. A run starts only in a session of the architecture it was recorded on.

    The name is optional, so leave it off and Machine makes one up. Machine waits until the session is running and tells you when it is. Add --no-wait if you would rather it didn’t.

    Then Machine uses the new session in this terminal, so your next command goes to it. Add --no-use to keep using the session you are on. A session created with --no-wait is not running yet, so it is not used.

    Your first session also sets up your account’s storage, so it takes longer to create, and Machine shows this as a step of its own. To set the storage up before that, run machine account provision.

    A machine takes its memory plus 128MB of the session’s memory, and 256MB of a session is not available to machines. A machine with the default 256MB needs 384MB, and one created with --mem 2048 needs 2176MB, so a 4G session holds one and an 8G session holds three. A machine holds its memory until you stop it, whether or not its program has finished.

    A branch you move onto with machine go uses the machine that is already running, so it needs no more memory. A branch you start with machine fork is another machine and needs its own.

    machine runs --size adds two columns for what a run takes of the session’s resources. RAM is the session memory its machine holds right now. It can be above the machine’s own MEMORY. DATA is what the run holds on the session’s disk. A run with no machine shows — for RAM.

    The MEM column of machine sessions list shows the memory taken over the session’s memory, for example 4.5G/8G with two machines of 2048MB. A new machine starts when what it needs fits in the rest, and is refused when it does not.

    To switch to another session, tell Machine which one to use.

    machine sessions use applies to the terminal you ran it in. If you only have one session, it needs no name at all. After that, every command that needs a machine goes to ci-1. You can send one command somewhere else with -s, for example machine -s ci-2 runs. -s goes before the command.

    Running a machine

    Creating a run

    machine create makes a run from a disk and boots it. The run’s name goes first and is optional. Without one, Machine makes up a name.

    The defaults are 1 CPU and 256 MB of memory. A few other options are worth knowing about:

    Option What it does
    --no-daemon boot and run to the end by itself, instead of waiting for your commands
    --pin-cpu n run on host CPU n, for this start only (the default picks the least-loaded)
    --like run start from another run’s options, then apply the ones you give
    --label name=value attach a label to the run, as many times as you like
    --rng, --rng-seed n an RNG device, on by default, seeded with n; the default seed is 0, and --no-rng leaves the device out
    --fs-sync write to the disk as the program writes, instead of later

    --disk-hash hash the machine’s disk at every entry, so a replay compares it too (off by default)

    Driving it

    A run executes only while you drive it. machine run is the way, and --until says when to stop. (A run created with --no-daemon answers ✗ Machine not in control mode, because the machine isn’t waiting for you.)

    A plain machine run can stop before the point you are waiting for. With --until, Machine keeps going until what you asked for is true. If it never gets there, the command exits with status 3.

    These are the conditions you can wait for. machine run --until and machine wait --for take the same ones.

    Condition True when
    running, paused, stopped, halted the machine is in that state
    ready the machine accepts commands
    tasks Linux is up and its task table can be read, which is before it starts anything in userland
    console~REGEX the console output matches the pattern
    ttyS1~REGEX the output of another source matches it, here the serial port ttyS1
    entry>=N the log has reached entry N
    entry=+N N more entries have been recorded
    vtime>=T the machine’s clock has reached T, a duration such as 500ms
    vtime=+T the machine’s clock has moved T from where it was
    /app:exit the program at /app has exited

    The last row is one example of a task condition. There are more of them under Steering programs.

    The two commands read a text condition differently. run --until waits for text printed during the run, so a line already on the console does not end it, and the same --until can stop at the next of several lines alike. wait --for asks whether the text has been printed at all, before the run or during it:

    A source name with a ~ in it is quoted inside the pattern, as in '"/output/keep/app/app.log~"~ERROR'.

    --iters limits how many iterations a drive may spend, and the global --timeout limits how long you are willing to wait. Whichever hits first wins.

    An iteration has no fixed length. It is one dispatch of a vCPU, and it ends where the guest next exits to the machine: after five instructions or after a million. So no count is right in advance, and nobody can know how long a program will run. Stop on a condition, and use --iters or a vtime condition as a limit. Every run ends by saying how far it went:

    vtime is how far the machine’s clock moved. A vtime condition is checked between iterations, so the run stops at the end of the iteration that reaches the time, a little late. A run that went too far is not lost: machine rewind and machine go take it back to an earlier point.

    A time bound

    --within ends a run when the machine’s clock has moved that far:

    Alone, it is the same run as --until vtime=+10s. With another --until it is a bound on it: if the clock gets there first, the run ends with exit status 3 and says Machine time ran out. The machine checks the bound itself, so a slow host does not end the run sooner, which the global --timeout in seconds would.

    The clock moves as the programs in the machine work and while the machine is idle. A loop that does nothing but spin does not move it.

    Now and then the host interrupts an entry while it is being recorded. Machine records that entry again, and you see nothing except a short pause. --retry sets how many more times one entry is tried, 2 by default. If they are all interrupted the run stops with Host interrupted the run at entry N. It is not recorded. and the machine rewind command that puts the run back at the entry before.

    Schedules

    A program that uses threads can behave differently depending on how they interleave. Machine can draw how long each stretch of execution lasts, so every run explores a different interleaving, and --seed makes those draws repeatable.

    --mode is how the machine runs: fast, step, step-into, free or fence, or a comma list to draw from. --step and --fast give the length of a stretch in each mode, as a number or a range like 1:200. --strategy sets how the draws are made, random (the default), golden or sweep, and --seed is the seed for the random and golden ones.

    A fence stretch ends in the same place every time the same state is recorded, where a fast stretch ends close to its length but not always at the same instruction. That exactness makes a fence stretch somewhat slower than a fast one. Give its length with --fence or --limit. Recording that repeats shows how to make a whole run record the same way every time.

    What a task does

    Drawing the length of a stretch varies where threads are interrupted. To vary what the guest’s scheduler does with them, draw a mark for the task on the vCPU at each dispatch:

    --task-sched draws among keep, hold, yield, drain and drain-all: hold takes the task off the run queue, yield puts it behind its peers, and keep changes nothing. --task-slice draws how long the task runs before the scheduler decides again, from a span such as 10us:600us, and default puts the kernel’s own back. --task-int draws whether to preempt it. Each takes a colon list to draw from, and --seed makes the draws repeatable.

    --when applies the draws only while a predicate holds, such as /usr/bin/app:on for the program running its own code. A predicate on a program needs the program focused first, as the second example does with machine focus, and the run refuses it otherwise. To draw different things at different moments, write a plan, where each clause has its own when.

    Combine that with branches. Fork several from one checkpoint, give each its own seed, and keep the ones that crash. The explore_seeds.py example in the SDK does exactly that.

    To hold an interrupt a drawn time before it is delivered, see Holding interrupts.

    A run takes checkpoints for you too. --auto-checkpoints N takes one every N entries, and 0 turns them off.

    If a drive or a checkpoint is taking too long, machine cancel app cancels whichever one is in progress.

    Recording that repeats

    A replay always repeats a recording exactly. Recording the same run a second time is different: by default two recordings of one run, from the same disk and the same seeds, start out the same and then drift apart a little.

    When you need the second recording to match the first, create the run with --repeatable. Every recording of it then records the same entries, whether the run has one vCPU or several, and a branch you fork from one of its checkpoints records exactly what its parent recorded after that checkpoint.

    Repeatable recording is slower, and how much slower depends on the program. Booting PostgreSQL 17 on one vCPU took 1 minute 10 seconds to record with --repeatable and 14 seconds without it. Loading its test data with pgbench -i, which computes with hardly a pause, took 1 minute 20 seconds against 4 seconds. A program that spends its time waiting on the disk, the network or a timer pays much less. Replaying a repeatable run is as fast as replaying any other.

    --timer-slack is how late a timer may be while a program runs code that takes no exit. The default is 20ms, and it applies to every fast run. A timer that comes due in code that does exit is delivered at that exit. 0 keeps every timer on time, which records slowest. A drive can draw the slack for that drive:

    --limit-margin is how many conditional branches short of an exact stop the CPU’s counter interrupts. The default is the host’s, and machine describe shows that default as host's. A smaller margin records faster. One too small misses stops, and a later recording may not repeat. machine replay --limit-margin sets it for that replay.

    A branch keeps its parent’s --repeatable, --timer-slack and --limit-margin unless you give it others. machine fork, machine detach and machine go take the three. machine start keeps what the run was created with.

    What you send a run is part of what a recording repeats. Commands given with machine exec, put and get in the same order at the same points name their processes alike in every recording, such as 40787p1: the entry the run stood at, and the command’s place among those sent there.

    Time compression

    Idle time takes almost no time.

    When every vCPU is halted and waiting for a timer, the machine doesn’t sit through the wait. It moves its clock straight to the earliest timer the guest armed, and the guest wakes up at exactly the time it asked for, as if it had waited. No instruction runs in between, so there is nothing for the host to do. Time the guest spends working is never skipped.

    Waiting

    machine wait doesn’t drive anything. It watches a run, or several, and returns when a condition holds.

    It exits with 0 when the condition is true, 2 on an error and 3 on a timeout, so scripts can tell them apart. Remember that it only watches. Waiting for a condition on a run nobody is driving never finishes unless you set --timeout.     Stopping and starting

    pause freezes a running machine and resume lets it carry on. kill ends it abruptly, where stop shuts a run down and keeps everything it recorded. In a session, both wait until what the run recorded is saved to your storage, and show how far the save has got. start brings it back at the end of its log. If the run had gone past its last checkpoint when it stopped, Machine replays the recorded tail from that checkpoint and tells you how many entries it replayed. Add --no-recover to make it refuse instead.

    start can also take a run back to an earlier point. --at replays from an earlier checkpoint, and --read-only opens a checkpoint without running it at all.

    --at brings the run up at the checkpoint and replays every entry after it, so the run ends at its tip as it would have without the option, and you see that the recording still replays. A read-only run accepts commands that read, such as machine dump, machine hash and machine output, and refuses run and anything that would record. Stop it, and start it again without --read-only to go on.

    A run remembers the options you created it with: --no-daemon, --single-step, --limit and --backstop-limit. Every start and fork repeats them, so you type them once. start takes the same flags to change them for that start only, so machine start app --daemon gives you a machine to drive on a run created with --no-daemon. fork and detach take them too, and the new run keeps what you gave. --pin-cpu is the exception: no run remembers a CPU, so each start and fork picks the least-loaded one unless you name it.

    Checkpoints and branches

    Branching is cheap, because a branch shares its parent’s history instead of copying it. That is what makes it practical to try many things from one point.

    Starting a branch

    machine fork creates a new branch at a point. The branch runs in its own machine, alongside its parent, and the parent keeps running.

    Give a branch a name with --name. If you don’t, it is named after the entry it landed on. Add --no-start to create the branch without starting it.

    A branch’s full name is the name of the run its tree starts from, a slash, and the name you gave it.     Moving the machine

    machine fork gives the new branch a machine of its own and leaves you where you were. go, switch and rewind work in place instead: they change the machine you are on. detach is the odd one out, and is explained below.

    Command Does
    machine go app ^booted creates a branch at a point and switches this machine onto it, in place
    machine switch app app/try-1 moves the machine onto a branch that already exists, and never creates one
    machine detach app --at ^booted copies a point into a new root, a self-contained run in a tree of its own
    machine rewind app to ^booted puts the run back at a point and throws away what came after

    go is the one you will use most. It creates a branch the way fork does, but it doesn’t start another machine. It moves the one you are on, in place.

    After a go or a switch, the run you moved away from is listed as switched and no longer running. machine start app brings it back at its tip, and tells you how many entries it had to replay to get there. The machine you moved is now the new branch, so talk to it by that name: app/g1.

    A switch needs a branch that isn’t running somewhere else. Pointing it at a branch that is gives ✗ Already running, so stop that one first or create it with --no-start.

    rewind changes the run itself, not a copy of it. Use it when you want to replay from an earlier point. The run keeps its name. Machine refuses to rewind past a branch that starts after that point, since that branch depends on entries that would no longer exist.

    switch takes a branch name, a mark (%crashed), parent or root.

    detach is for leaving a tree behind. A branch normally shares its ancestors’ data, which is what keeps it cheap. detach copies everything into a new root that owns all of its data and belongs to no tree but its own. That is much slower than a fork, so only reach for it when you want to get rid of the original.

    Replay

    Replay is what makes a recording useful. A branch can play back what its parent recorded and Machine checks, step by step, that it gets the same result.

    Replay is strict. An entry that does not reproduce what was recorded means the run has diverged. Before giving up on it, Machine replays that entry again from the nearest checkpoint before it, twice by default. Use --retry to change that, or --retry 0 to try each entry once.

    --to stops at a point instead of the end. It takes a point as every command does: --to ^booted for a checkpoint, --to '#300' for an entry, --to 10ms for a time. The point is one of the line being replayed, so a checkpoint the parent took after the fork is a valid one. --trace replays one iteration at a time and prints each entry as it goes, which is slower.

    Each entry holds hashes of the machine’s state: its registers, its devices and its timers. A replay compares them all. A run created with --mem-hash also hashes the guest’s memory at every entry, and one created with --disk-hash its disk, and a replay of it compares those as well. Hashing costs time at every entry, so both are off by default. A divergence of memory or the disk alone then shows up later, once it reaches a register or a device. A branch can turn either on or off:

    A replay hashes memory and the disk exactly where the recording did, whatever the replaying branch records, so a replay compares either kind of recording. diff of an entry that hashed one against an entry that did not leaves it out, and says Memory not compared or Disk not compared.

    The host can interrupt an entry too. That is not a divergence. Replay prints Interrupted: entry N, crossing 1: host SMI and replays the entry again, counted against the same --retry. A recording does the same on its own, see Driving it.

    If a run does diverge, machine diff shows how.

    With no second argument, diff compares the entry against the run it was replayed from, and says ✔ No differences when they match. Otherwise it prints a hash by default, and --show takes any of the sections in its help: registers, stack, page tables, timers, devices, memory and more. Name another run to compare two recordings. A difference there only means the recordings differ. It says nothing about determinism.

    There is also machine play, which plays a log back without checking for divergence. It is for when you want to see what happened, not whether it repeated. By default it plays the parent’s log, so it needs a branch. To play another run’s log, name it: machine play app/try-1 app.

    --include plays only the kinds of entry you name, and --exclude plays every kind but those.

    Comparing two machines

    machine diff compares an entry with the one it was replayed from. machine hash compares two machines stopped at the same point: a recording, and a branch you drove there yourself.

    The command computes the hashes of the machine as it stands: memory, the disk, each device, each part of each vCPU, and the interrupts --irq-delay holds, as irq_pending. It changes nothing, and the run records nothing. Memory is read from all of RAM, so it takes as long as that reading takes. The machine refuses commands that would change it until the command returns. machine cancel stops it.

    machine dump --show hash prints what the newest entry recorded, before its exit was handled. Memory and the disk are 0 there unless the run hashes them at each entry. machine hash is after that entry, with the exit handled, and it hashes memory and the disk whether or not the run does at each entry.

    A replay compares the hashes the recording stored at each entry. hash is for two machines you have in front of you.

    Plans

    When one rule isn’t enough, write a plan file. A plan is a list of clauses, and each one says when it applies and what to do.

    Machine tries the clauses in order and the last match wins, so a later clause overrides an earlier one. else covers whatever nothing matched.

    Each when names a state of a program (/test:on is the program running its own code, and /test:kernel is the program running in the kernel). After that come the things to choose for each stretch of execution it covers, such as the mode, how many instructions to run, or what to do with the scheduler. machine plan --help lists all of them.

    A clause draws any of these, once per dispatch:

    Axis Draws
    mode how the machine runs: fast, step, step-into, free, fence or keep, with the length of a stretch as fast=1:100k
    task-sched what the task on the vCPU does: keep, hold, yield, drain, drain-all
    task-int whether to preempt that task: none or preempt
    task-slice how long that task runs between decisions: keep:default:10us:600us
    task-pin where a task goes when it next wakes: a vCPU set, free or none
    vtime-rate how fast the machine’s clock passes, as in Clock rate
    vtime-add time added to the clock before the dispatch, such as 10us:2ms
    timer-slack how late a timer may be, such as 0:20ms
    irq-delay how long each interrupt is held, as in Holding interrupts

    Every axis but task-slice is a comma list of choices, and [N] makes a choice N times as likely: mode step[3],fast[1] draws step three times as often as fast. keep draws nothing and leaves the axis as it was, so a clause can leave an axis alone part of the time. A range such as 1:200 draws one value from it, and the plan’s --seed makes every draw repeatable.

    A when names what a task is doing: /path:on for a program running its own code, /path:kernel in the kernel, /path:syscall=openat in one system call. The subject can also be tid=N, tgid=N, comm=NAME or cgroup=PATH, and vcpu=1 narrows it to one vCPU. Braces may group a clause, # starts a comment, and a file named - is read from standard input.

    The plan applies to the run of that machine plan command alone. A later machine run runs without it.

    From Python, run.plan("plan.txt", seed=3) runs a plan from a file, and the RunResult it returns lists each clause with the iterations it applied to. The plan_file.py example shows one.

    Fault injection

    machine inject makes things fail inside the machine. A fault goes into a subsystem: a program’s system calls, or one of the kernel’s own places where things can fail, such as the disk or memory allocation, or the disk itself. You find out what your program does when openat says EACCES, write says ENOSPC, the disk returns an I/O error, the kernel runs out of memory, or the disk quietly returns the wrong bytes, at the call you choose or by chance.

    Subsystem What fails
    syscall a system call returns an error you choose, or waits first
    disk a disk read or write returns an I/O error
    disk-timeout a disk request never completes, and its task waits forever
    slab, pages a kernel memory allocation fails, usually as ENOMEM
    usercopy the kernel fails to copy to or from the program’s memory: EFAULT
    futex-access a futex call fails to reach the program’s memory: EFAULT
    disk-corrupt a disk read or write succeeds with bytes changed
    disk-torn a write succeeds, but only its first sectors reach the disk
    disk-lost a write succeeds, and none of it reaches the disk

    Every subsystem takes the same options: --in for whose calls, --prob for the chance, --after to let calls through first, --times to stop after a number, and --seed. The disk subsystems also take --file, --op and --sectors to say which requests. The guest kernel decides each call itself, without stopping the machine, and a replay fails exactly the same calls.

    Kernel faults

    The other subsystems fail work inside the kernel, after a system call has started, where a syscall fault never reaches. They take no errors: each fails the way the kernel would.

    A few things decide whether you see the failure:

    • Who sends a disk request. Your program sends its reads, its O_DIRECT writes and the writes fsync forces, so --in /usr/bin/app fails those. Ordinary writes wait in memory and the kernel’s flusher writes them later, so only --in all reaches them.
    • A program’s first moments. When a program starts, the kernel copies its arguments in and allocates for it. A usercopy or allocation fault that fires then kills the program before your code runs. Use --after, or add the fault once the program is up.
    • The kernel copes with some failures. A failed page allocation is often retried, and the program never sees it. MATCHED and FIRED in the list still show that the fault fired.
    • The kernel reads a page twice. A buffered read goes out as readahead, and when that fails the kernel reads the page once more before it gives up. disk --times 1 fails only the first try, so your program reads the file fine; that is the kernel recovering. Use --times 2, or no limit, for the program to get EIO. An O_DIRECT read fails on its first request.
    • disk-timeout hangs. The request is lost, and the task waiting for it stays stuck until the machine stops. That is the point: you find out what else in the program notices. Name your program in --in: with --in all the lost request may be the kernel’s own, and whatever waits on that disk hangs with it.

    Damaged data on the disk

    The faults above are errors: your program is told something failed. Real disks also fail silently. A write reports success and the data is wrong, half there, or not there at all. disk-corrupt, disk-torn and disk-lost are those failures. The request succeeds, and the damage is found later, or never.

    You want to know Fault
    Does the database notice a bad block when it reads its data files? disk-corrupt --file '/var/lib/db/*/data.bin'
    Does the program trust bytes it read without a checksum? disk-corrupt --op read --file /srv/app/state.json
    Does recovery handle a log record only half written? disk-torn --file /var/lib/db/wal --times 1
    Does it notice a committed write that never arrived? disk-lost --file /var/lib/db/wal --after 10 --times 1
    Does the filesystem survive damage to its own metadata? disk-corrupt --sectors LO:HI, the sectors of its inode table or journal
    • --file is a pattern. * matches within a directory and ** across directories. Programs often name their files as they run, and a pattern names them before they exist. A file the program already holds open or maps, such as a running database’s WAL, matches too. A file inside a container is named by its path in the container.
    • --in all with --file. Ordinary writes reach the disk from the kernel’s flusher, not from your program, so --in all is what reaches them. --file keeps the fault on your file.
    • The page cache hides a damaged write. The kernel keeps the bytes your program wrote in memory, so the program reads them back clean until they are read from the disk again: after a restart, after echo 3 > /proc/sys/vm/drop_caches, or in a branch forked later. A damaged read is the other way round: the bad bytes go into the page cache, and every reader sees them until the kernel drops the page.
    • A tear is whole sectors. A sector is written whole or not at all, so a write of one sector does not tear. A torn write keeps at least one sector of the new data and loses at least one.
    • --sectors aims below the files. It names 512-byte sectors of the whole disk, so it reaches what --file cannot: the filesystem’s inodes, bitmaps and journal. The filesystem’s own tools say where those are, such as dumpe2fs and debugfs for ext4, in blocks of its partition. With 4 KiB blocks, block N starts at sector 8 × N plus the partition’s first sector, which /sys/class/block/vda1/start holds, or 0 for a filesystem on the whole disk. Or stop at a write with catch add io, below, and read its sectors off the stop.
    • disk-lost is one write, not a crash. The lost write reports success, and the writes after it still land. A power cut loses every write since the last flush. Machine does not offer that.

    What a fault misses

    • A C function is not always the system call of its name, and C libraries differ. glibc’s open() calls openat, musl’s calls open, and glibc’s stat() calls newfstatat. Name both, open,openat, to cover either. machine syscalls app lists the names the kernel uses.
    • Give --seed in a script that records again. Without it each run draws its own seed. A replay needs none: the run keeps the fault as it was added.

    A crash

    kill loses nothing the program wrote: the kernel inside the machine keeps running and writes it out later. crash is a power cut of the service’s node.     Debugging

    There are two ways to debug a program in a machine. The machine’s own debugger works from outside the guest: machine regs, mem, step, break and the rest read and change a task while the machine is stopped, and they work on any program, including one with no debugger on its disk. GDB works from inside: install it on the disk, attach it with gdb -p, and use it as on any Linux host.

    Both are recorded. A replay repeats every step, every write and every stop, and a checkpoint taken before a session lets you run it again from the same state.

    The machine’s debugger

    Each command takes the run and a task by its tid, which machine tasks lists. A task’s tgid is its process. The commands work while the machine is stopped, between runs, on a task that is on a vCPU or off one.

    Symbols, types and source lines come from the program files on the machine’s disk: the program’s symbol table, and its debug information when it has some.

    Breakpoints, watchpoints and catchpoints

    A breakpoint stops the run when a task of its tgid reaches its location. A watchpoint stops it after an instruction writes the bytes it watches. A catchpoint stops it at an event of a task: an exec, an exit, a fork, a system call, a signal, a file mapped or a C++ exception.

    watch add takes --on write, change, read or access, and --size for a location that is not a variable. An exit catchpoint takes --in tgid=N, since an exit is the end of a process. A throw, catch or rethrow catchpoint needs --in tgid=N.

    --in comm=NAME stops at the events of the tasks with that name, the same tasks machine tasks app exist comm=NAME lists. That catches one tool of a busybox, or a script, before you know its ids. An exec catchpoint sees the new program’s name. An exit catchpoint sees the name of the process’s main thread, which ends last, so a worker thread named cat inside a differently named process does not stop it. A syscall catchpoint with a name makes the machine report every task’s calls while it is set, which costs time on a busy machine.

    Each stop has a number, and the same verbs change any kind:

    machine break, watch and catch each list their own kind.

    A run that reaches a stop ends there and says which. The run log keeps the stops: a branch has the ones its parent had where it was forked, and a replay applies the adds and deletes. The stops are armed while the run records, and not while it replays.

    Hardware breakpoints

    A run has 3 debug registers for its stops. These take one each:

    • a breakpoint or a watchpoint of machine break add or machine watch add
    • the stop of run --until tid=N:at=LOC, write=LOC or access=LOC, for that run
    • a throw, catch or rethrow catchpoint

    Reading the disk

    You can read files from a run’s disk without touching the run. machine fs reads the filesystem on the disk as a checkpoint saved it, so it never changes how the machine executes.

    Every read names its checkpoint with --at, as a point: ^booted for a checkpoint by name, or '#4200' for the checkpoint at an entry. There is no default. This is not a view of the running machine, and a listing that did not say how old it is would read as one.

    A point with no checkpoint at it is refused, and the refusal names the checkpoint before it.

    Data the machine has not synced to its disk is not visible. A file a program wrote a moment before the checkpoint can be missing, short or empty, because the machine still holds it in memory.

    machine fs

    List, copy or print files of a run’s disk.

    The command reads the filesystem on the disk as a checkpoint saved it. It never reads the live machine. It needs no program in the machine and does not change how the machine executes.

    Every read names its checkpoint with --at. A point that is not a checkpoint is refused, and the refusal names the checkpoint before it. The point now is the checkpoint the run stands at, until the machine runs again.

    Data the machine has not synced to its disk is not visible. A file a program wrote a moment before the checkpoint can be missing, short or empty.

    A run created with --fs-sync writes every change of a file to the disk as it is made. A run created with --fs-dirsync does so for every change of a directory. Both are options of create and are off by default.

    machine create

    Create a run and start it. See Creating a run.

    Options configure the machine: disk, memory, CPUs, devices and virtual time. The RNG seed and the virtual time base, rate and costs fix the sources of nondeterminism.

    Use --auto-checkpoints to set how often checkpoints are taken. Use --like to inherit the options of another run.

    The machine waits for commands. Use --no-daemon to run it to completion instead.

    The run keeps its execution options. Start and fork repeat them unless given others.

    A source is a device the machine prints on, such as ttyS1, or a file under /output. Use --keep-output to store a source that would be dropped. Use --drop-output to store less. The run keeps both lists for its whole life, and the describe command shows them.

    A run stores every source but the files under /output/drop. A file there has a name and no bytes. A program writes under /output/drop through MACHINE_DROP_OUTPUT_DIR. It writes under /output/keep through MACHINE_OUTPUT_DIR.

    A name given to either option may be a pattern, such as /output/drop//.log. A star matches within one directory name, a leading dot included, and never a slash. Two stars match any number of directories.

    A name given to --keep-output or --drop-output decides before the directory does. When a kept name and a dropped name cover one source, a name spelled out decides over a pattern. Of two names spelled out, the longer decides, and a tie keeps the source. Of two patterns, the kept one decides.

    machine run

    Run one or more vCPU iterations. See Driving it.

    The machine executes and the run log records each iteration, so the run can be replayed.

    The mode sets how an iteration executes. Fast mode stops near the limit, a little late. Step mode stops exactly. Step-into mode also steps into syscalls, gates and injected events.

    An iteration is one dispatch of a vCPU. It ends where the guest next exits to the machine, or at the limit. Its length is not fixed. One may be five instructions and the next a million.

    The run stops after --iters iterations or when the --until predicate holds. No count is right in advance, because how long a program runs is not known. Use --until to stop where something happens, with --iters or a vtime predicate as a bound.

    A run that went too far is not lost. Use rewind or go to return to an earlier point.

    A vtime predicate holds once the clock of the machine reaches a time. vtime>=T counts from the start of the run. vtime=+T counts from where the run is. The run stops at the end of the iteration that reaches the time.

    Options vary the run. They draw the mode, the limit and the virtual time rate. They also draw a scheduling mark, slice and interrupt for a task. The same seed draws the same values.

    The --until predicates are those of wait. The console~ predicate signals that boot is done. The halted and activity=idle predicates do not.

    A console~ predicate takes a regular expression. The run stops at the entry that ends the line the match is on. A match on a line with no end, such as a prompt, stops the run where the machine goes idle.

    The match is within a line, as output search finds it, and has at least one character. Use the point console~REGEX to go to the entry that printed the first byte of the match.

    The name of another source takes the place of console, as in ttyS1~REGEX. The run then stops for a line that source prints. A line another source prints does not stop it.

    The path of an output file takes the same place, as in /output/drop/app/debug.log~REGEX. A file that is dropped stops the run the same way. The run stores none of the file. A path that holds a ~ is quoted, as in ‘“/output/keep/app.log~“~ERROR’.

    Only text the run prints from its start ends it. A line printed before does not. Use machine wait --for to ask whether text was printed.

    tid=N:at=LOC runs until tid N reaches LOC in its own code. tgid=N:at=LOC runs until any thread of the process does. The address is resolved when the run starts. The stop takes one of the run’s 3 breakpoints and watchpoints.

    tid=N:write=LOC runs until an instruction writes the bytes LOC names while tid N is on a vCPU. tid=N:access=LOC runs until one reads or writes them. tgid=N:write=LOC and tgid=N:access=LOC stop for any thread of the process.

    The run stops after the access. A write the kernel makes for the task counts. A variable or an expression is watched at its size of 1, 2, 4 or 8 bytes. The watch takes one of the run’s 3 breakpoints and watchpoints.

    An address is watched through a cast that gives it a type, as GDB’s watch takes one. The address is a multiple of the size. tgid=N also stops for a kernel thread that works in the process’s memory.

    A run that stops at LOC says the tid that reached it and where it stands. A watch also says the value the access left in the bytes. The machine records both at the stop, so a task in the kernel still shows them.

    LOC is one of these, in the task’s process:

    The run log records each iteration as an entry. It also records interrupts and device input, so entries outnumber iterations.

    The global timeout cancels the run in flight. Without one there is no limit. A timeout of 0 checks once without batching. Exit 3 means the predicate was not reached.

    --iters is an upper bound, not a count. A batch is the iterations one request of the command runs. It ends at every context switch of a focused task, a task the focus command names. It also ends where a task reaches its own code.

    Without --until, a batch that ends early ends the run. With --until, the run goes on with the next batch. The response reports how many iterations ran.

    Every parameter is drawn for one iteration. The mode, the limit, the task marks and the interrupt apply to the task on that one vCPU.

    Without --vcpu, a scheduling cycle dispatches every vCPU. It spends up to one iteration for each. --iters 100 on four vCPUs buys 100 dispatches, not 400.

    With --until, --iters and the predicate are both bounds. The first to fire wins. --iters 500 --until on stops at 500 iterations or when a focused task takes a vCPU.

    Use --within to bound the run by the machine’s clock. The machine checks the bound at every iteration, so a slow host does not end the run sooner. With --until, the first of the two to hold ends it. Without --until, the run goes on until the clock has moved that far.

    Without --iters, only the timeout bounds the run, so --until tasks runs a whole boot. A span is lo:hi, a range one value is drawn from for each dispatch. A span bounds nothing either, so --iters 100:500 --until on keeps going.

    --when bounds nothing. It names what must be true for the clause to apply to a dispatch. A dispatch it excludes runs free, up to the crossing into the subject.

    So --when /test:on --until /test:exit perturbs that program while its own code runs. It runs free while the program is in the kernel or off the CPU. It stops when the program is gone. --iters counts every dispatch, the ones that ran free too.

    --when takes on, kernel and off. Each is a state, not an edge.

    The options of run make one clause of a plan. Use machine plan <run> <file> for a run of more than one clause.

    A hit of a breakpoint, watchpoint or catchpoint ends the run. Use --iters 0 to run until one does, as GDB’s continue does.

    Use --back to go back to the newest breakpoint, watchpoint or catchpoint hit before now, as reverse-continue does. The machine switches onto a branch at that entry, as go does. The branch keeps the run’s stops as they are now. The run stays as it was.

    machine wait

    Wait until a run satisfies a predicate. See Waiting.

    Use wait to script against a run. It waits for a state, an entry, a console line or a task event. Several runs, or every run of the session, may be waited for.

    The predicates are running, ready, tasks, stopped, paused, halted, activity=<name>, entry>=N, entry=+N, vtime>=T, vtime=+T, console~REGEX and a task predicate. The tasks predicate holds once the operating system is up and its task table is readable. That is before it execs anything in userland.

    A console~REGEX predicate holds once the console prints a match. The name of another source takes the place of console, as in ttyS1~REGEX.

    A task predicate is [who:]what. The what is exec, exit, sched, desched, on, kernel or off. The who is /path, cgroup=path, comm=name, tgid=N or tid=N. Omitting it means any focused task.

    A path, a cgroup or a comm must already be focused. Such a subject means its tgid. tgid=N means the tgid for exit and any of its tasks for exec. Use machine tasks <run> --focused to see which task is on a vCPU.

    Four of the seven are edges. exec fires where a task matching who entered the task table. exit fires where one left it.

    sched fires where a task is given the CPU. desched fires where one gives it up.

    Three are states, and they partition time. on holds while the task is on cpu in its own code, at CPL 3. That is where a forced decision can land between two of its own instructions.

    kernel holds while that task is on cpu in the kernel. off holds while it is not the task on cpu at all.

    Named runs must be in the current session. Use --all to wait for every run in it.

    The global timeout bounds the wait. Without one there is no limit. A timeout of 0 checks once.

    machine replay

    Replay recorded entries from the parent lineage. See Replay.

    The command executes the recorded entries again. During replay, Machine checks each entry against the original recording. If they don’t match, Machine reports a divergence. It names the entry, with the expected and actual values.

    Without a line, the parent’s entries are replayed. A fork at an entry leaves that entry with the parent. The branch starts at the next entry, so the entries of the parent end at the fork. Replaying past them reports no forward entries.

    Use --to to stop at a point of the line that is replayed. The point is an entry, a checkpoint or a time of that line. A checkpoint the parent took after the fork is such a point.

    The line of a run is its entries from the root on, across every fork. Naming a run replays the entries of its line. The run must be in the same tree. The entry this run stands on must be on the line replayed.

    An entry that diverges is replayed again from the newest checkpoint before it, at most twice. It is not replayed again once it diverges the same way twice. An entry that the host interrupted is replayed again the same way. It is not a divergence.

    Use --retry to set how many retries. --retry 0 replays each entry once. Use --limit-margin to set how many conditional branches short of each recorded entry the CPU’s counter interrupts. A smaller margin makes a miss more likely.

    The replay stores what the branch keeps of its output. A branch that keeps an output file its parent dropped is how the file is read. Use fork with --keep-output to make one. What is stored does not change what the machine executes.

    machine fork

    Fork a branch and start it alongside the parent. See Starting a branch.

    A branch shares the history of its parent up to the fork point. Then it runs on its own path. Use --rebase to copy the data of the ancestors instead of sharing it. Use --no-start to create the branch without starting it.

    The parent keeps running. The terminal stays attached to the parent.

    The branch forks at the current point and reuses a checkpoint there if one exists. Use --at to fork at another point.

    The branch keeps the execution options of the parent. Options given here replace them for the branch.

    The new run keeps and drops the output that the run it comes from does. Use --keep-output to replace the names it keeps. Use --drop-output to replace the names it drops. Each option changes its own list only.

    Use --from to replay the new run from an earlier point to its point. The new run stores the output of that stretch by its own names. It is forked at the checkpoint at or before the earlier point.

    A run stores every source but the files under /output/drop. A file there has a name and no bytes. A program writes under /output/drop through MACHINE_DROP_OUTPUT_DIR. It writes under /output/keep through MACHINE_OUTPUT_DIR.

    A name given to either option may be a pattern, such as /output/drop//.log. A star matches within one directory name, a leading dot included, and never a slash. Two stars match any number of directories.

    machine go

    Branch at a point and switch onto it. See Moving the machine.

    Go starts another path from a point. The branch shares the history of the run up to the point.

    The machine moves onto the branch. The run it leaves is listed as switched. A switched run keeps its history and has no machine.

    Go is the only command that branches and switches in one step. The point operand lists the forms a point takes. Each names a point on the own line of this run.

    console~REGEX is where the console first printed a match. It is the entry that printed the first byte of the match. The name of another source takes the place of console, as in ttyS1~REGEX.

    A time such as 10ms counts from the start of the run. A minus sign, as in -10ms, counts back from now. A time may carry +N, as machine now prints it, to name one entry among several at that time.

    A minus sign before a number with no unit counts entries back from now. The point -10 is #-10, 10 entries before now.

    Go reaches a point that is not a checkpoint by branching at the nearest checkpoint at or before it. It then replays the difference.

    Every use creates a branch, also for a point gone to before. What runs from a point is a path of its own. Use switch to return to a branch that exists. Use rewind to put this run back at a point.

    The new run keeps and drops the output that the run it comes from does. Use --keep-output to replace the names it keeps. Use --drop-output to replace the names it drops. Each option changes its own list only.

    Use --from to replay the new run from an earlier point to its point. The new run stores the output of that stretch by its own names. It is forked at the checkpoint at or before the earlier point.

    A run stores every source but the files under /output/drop. A file there has a name and no bytes. A program writes under /output/drop through MACHINE_DROP_OUTPUT_DIR. It writes under /output/keep through MACHINE_OUTPUT_DIR.

    A name given to either option may be a pattern, such as /output/drop//.log. A star matches within one directory name, a leading dot included, and never a slash. Two stars match any number of directories.

    machine hash

    Show the state hashes of the machine. Each is computed as it stands. See Comparing two machines.

    The command prints a hash of memory. It prints a hash of the disk. Each device has a hash too. The interrupts run --irq-delay holds have a hash, irq_pending.

    machine profile

    The machine samples each CPU at every timer interrupt, 250 times a second. Nothing runs in the guest for it. The command prints the functions that ran. Each has the share of samples it ran in and the share it was on the stack of.

    machine inject

    Inject faults into the guest’s system calls and kernel.

    A fault makes a system call fail with an error, or wait. A fault at a kernel site fails a disk request or drops its completion. It also fails an allocation of the kernel, or a copy to or from a program’s memory. The guest kernel decides at each call, without a stop of the machine.

    A replay acts on the same calls the same way. The faults are part of the machine. A checkpoint keeps them, and a fork has its parent’s. The run records each change, and a replay makes it at the same point.

    Use --in to say whose calls a fault acts on. It is required. A program is the absolute path of the file it runs, the EXE that tasks shows. It takes the tasks running that file, and the processes they fork without exec.

    machine step

    Step a task.

    A step is one instruction of the task. Use --line to step a source line. Use --over to step over a call, so the function and all it calls are one step. Use --out to run until the function returns.

    The machine runs whichever task the guest schedules. A step of one task runs the machine until that task is in its own code, then steps it. Other tasks run meanwhile.

    Each step runs the machine, and the run records it, so a replay makes it again. A breakpoint the step reaches ends it. A line step steps out of a function that has no line tables.

    Use --skip NAME with --line to step out of a function or a source file of that name. It does as GDB’s skip does. Give it once for each name.

    Use --back to go back over dispatches of the vCPU the task is on, as reverse-stepi does. A dispatch is one entry into the machine, one instruction where the run stepped. The machine switches onto a new branch there, as go does.

    With --line, --over or --out, --back goes back over the task’s own code. It does as reverse-step, reverse-next, reverse-nexti and reverse-finish do. It goes back over what the run recorded one instruction at a time. Past that it stops, and says the history ends there.

    machine catch add

    Add a catchpoint.

    The catchpoint stops the run at an event of a task. The events are exec, exit, fork, vfork, syscall, signal, load, unload, fault and io. The C++ events throw, catch and rethrow are breakpoints in one tgid.

    A fault catchpoint stops where an injected fault fires. A syscall fault stops before its delay and its error. The hit names the call and the error, or delayed for a fault with no error. A site fault stops at the site, and the hit names the site.

    An io catchpoint stops at a disk request as its task submits it. No disk fault has decided on the request yet, so a fault added at the stop decides on it. The hit names the request’s operation, sectors and tid in the form inject add takes them.

    Use --file to stop at the requests of the files a pattern matches, and --op for reads or writes alone. A file matches whether it is opened or mapped before or after the catchpoint is added.

    A syscall catchpoint names its system calls, and a signal catchpoint its signals, four at most. A fault catchpoint names system calls or the sites of inject add, such as disk. A load, unload or exec catchpoint names a path or a file’s name. Without one, every event of its kind stops the run.

    Use --in to stop at the events of one task or one tgid alone. The run log keeps the catchpoint, and a branch has its parent’s.

    Use --in comm=NAME to stop at the events of the tasks of that comm. The comm is read as tasks exist reads it. An exec catchpoint sees the new program’s comm. A task renamed after exec is seen by its new comm at the next fork, exec or exit.

    An exit catchpoint sees the comm of the tgid’s leader, its last task to go. A worker of that comm in a tgid whose leader has another does not stop it. A syscall catchpoint with a comm makes the guest report every task’s calls while it is armed.

    An exit is the end of a tgid, so an exit catchpoint takes --in tgid=N and not a tid. A throw, catch or rethrow catchpoint is a breakpoint at the C++ runtime’s function. It needs --in tgid=N and takes no values. It takes one of the run’s 3 breakpoints and watchpoints.

    Python SDK

    The SDK does what the client does, from Python. If you can type it in a terminal, you can call it from a program.

    Installing

    It needs Python 3.11 or later on Linux x86_64, the same systems as the client. If you need another platform, contact us. pip installs the Machine core that the SDK runs on, testflows.machine.core, along with it.

    Hello Machine

    This creates a session, boots a run from the disk hello and prints the last twenty lines of its console. A run waits for commands, so it moves only when you call run.run(...); pass daemon=False to have it run to the end by itself. Leaving a with block deletes what it created, whether the block ends normally or with an error. That is how you make sure a session never outlives your program.

    The same names

    Every client command has a matching SDK call, and the names follow a simple rule.

    In the client In the SDK
    a top-level command, machine create --disk app a method on the client, client.create(disk="app")
    a group, machine sessions use ci-1 an attribute of the client, client.sessions.use("ci-1")
    a command that takes a run, machine fork app --at ^boot a method on the run, run.fork(at="^boot")
    a group that takes a run, machine tasks app hold 56 an attribute of the run, run.tasks.hold(56)
    a positional argument a positional argument
    a flag like --no-wait, -w or -f a keyword argument like wait=False, watch=True or follow=True

    So once you know the client, you know most of the SDK. Commands lists them, and the client’s --help says what each call takes.

    Signing in

    The SDK signs in with an API key from TESTFLOWS_MACHINE_API_KEY if it is set. If it isn’t, it uses the login that machine login stored, which it shares with the client.

    A program can sign in on its own too. The one-time code arrives by email.

    machine.login.logout() signs out.

    A client has a current session, like the CLI does. You can set it when you create the client, or later.

    sessions.use only changes the session for this client. It never changes it for the machine command. Without a session you can still read your account’s runs: client.runs(), client.branches() and a run’s describe(), lineage() and checkpoints() all work.

    task.step(), task.step(line=True, over=True), task.finish() steps an instruction or a line, over calls, or out of the function
    task.back(), task.back(line=True, over=True) goes back over the task’s code onto a branch, as reverse-stepi and reverse-next
    task.call("strlen", "buf"), task.return_(0) calls a function in the task, or returns from its innermost one
    task.breakpoint("main"), task.watch("counter", on="access") stops its tgid at a location, or at a write or an access of its bytes; run.run(...).hits names the one the run ended at
    run.breakpoints.catch("fork", in_="tgid=1"), run.breakpoints.catch("io", file="/db/*/data.bin", op="write") stops at an event of a task: exec, exit, fork, vfork, syscall, signal, load, unload, fault, io, throw, catch, rethrow; in_ takes the words --in takes, tid=N, tgid=N or comm=NAME; file and op are an io catchpoint’s, as --file and --op
    run.breakpoints.list(), .enable(2, False), .condition(2, "n > 3"), .ignore(2, 5), .delete(2), .hits() the run’s stops, changed one at a time, and the hits the run log keeps
    run.run(iters=0), run.run(until="tid=412:at=main"), run.back() runs to the next hit, or until a task reaches a location; goes back onto a branch at the newest hit
    run.tasks.signal(412, "SIGTERM") sends a task a signal; a replay sends it at the same instruction
    run.start(), run.stop(), run.pause(), run.kill(), run.delete() lifecycle
    run.start(at="^booted"), run.start(at="^booted", read_only=True), run.start(recover=False) replays from a checkpoint to the tip, opens a checkpoint to read, or refuses to replay the tail, as machine start does
    run.fork(from_="^booted", name="b"), run.rewind("^booted") a branch forked at the checkpoint before a point and replayed to it; the run put back at a checkpoint
    run.sync(), run.cancel() publishes the run to your storage; cancels the drive or checkpoint in progress
    run.keep() keeps a run created in a with block when the block exits, such as one that just failed, with its tree
    run.marks.add("good"), run.marks.list(), run.marks.remove("good"), client.marks.list() names a branch, as Marks describes; the last lists every mark
    run.tasks.hold(56), .release(56), .yield_(56), .slice(56, "10us"), .pin(56, "2") steers one thread, as Holding threads describes
    run.syscalls.counts("/usr/bin/app"), run.ints.counts(...), run.vtime.add("5s") counts a task’s system calls or interrupts; pushes the clock forward
    run.debug.log(lines=-20), run.debug.err(), run.control.log() the run’s debug output, its error log, and the commands issued to it

    Every call returns a record with named fields, such as a RunInfo from describe() or a list of TaskInfo from tasks(). Call as_json() on one to get a plain dict.

    run.run(...) and run.plan(...) return a RunResult, which says how far the drive went. An iteration has no fixed length, so iterations alone does not tell you:

    Field Is
    iterations the iterations that ran
    vtime_elapsed how far the machine’s clock moved, in nanoseconds
    reached whether until held; False when iters ran out first
    clauses each clause the drive drew from, with the iterations it applied to
    entry_id the entry the drive ended at
    entries where each vCPU stopped
    hits the breakpoints, watchpoints and catchpoints the drive ended at; empty when none ended it
    printed the lines the stops that print printed, in the order they hit

    Points in a run’s history

    Calls that take a point, such as fork(at=...), go, rewind, replay(to=...) and profile(from_=..., to=...), take it as text, "^booted", "#300", "1.194s" or "-10ms", or as one of three records:

    Record Is Works on
    Point a time: vtime, the machine’s clock in nanoseconds every run; each finds its own entry at that time
    Place one entry: the run_id that recorded it, entry_id, point and vtime_offset the run that recorded it, and branches forked after it
    Checkpoint a saved state: its name, and the place it was saved at wherever its place works

    start(at=...) and the fs readers take only a checkpoint, by its name or as a Checkpoint: they open a saved state, and a time or an entry is not one.

    A point moves by a duration: an int of nanoseconds, a string such as "10ms", or a timedelta. Subtract one point from another for the nanoseconds between them. run.now() returns a Place, and run.place(point) finds the entry a point names.

    A place is one run’s entry, so once the parent and the branch have both run past the fork, run.place(here) is refused: the parent’s entry with that id is another state. Pass here.point to take the same time instead.

    Watching and following

    A listing takes watch=True and then gives you a new list every time something changes. A log takes follow=True and gives you new lines as they come, like tail -f.

    Choosing entries

    Anything that reads entries takes the same few spellings.

    You write Means
    200 or (100, 200) that entry, or that range, both ends included
    "100:200", "100:", ":200" a range, from 100 on, or up to 200
    "-20" or "-20:" the last 20 entries
    "-20:-2" the 20th entry from the end through the 2nd
    slice(100, 200) a Python slice, so 100 through 199
    slice(-20, -1) a Python slice from the end, so the same as "-20:-2"

    Be careful with the slice rows. A pair and a string include both ends, the way Machine’s own messages do. A slice is Python’s, so it stops before the end. That makes (100, 200) one entry longer than slice(100, 200).

    Both ends of a range count from the same end: "-20:5" and slice(-20, 5) are refused.

    lines= selects lines of output in the same grammar: 20 is line 20, -20 the last 20, "-10:-2" the tenth line from the end through the second, and 0 none, which starts a follow at the end.

    Cleaning up

    A session costs from the moment you create it, and a run keeps its log and checkpoints until you delete it. Both can be used as context managers, as in the first example, and deleting a run takes its branches with it.

    If you want to keep a run that found something, don’t wrap it in a with block. Nothing is deleted until you call delete().
